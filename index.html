Seerah QA Bot

★ Winner Live

A source-grounded conversational assistant for verified Seerah and Shamail content. It answers in-context questions, refuses out-of-scope fatwa requests by code, and cites corpus entries instead of trusting model output.

Problem

Generic LLM answers about the Seerah can be unsourced, hallucinated, or drift into religious rulings. Users need verified, citable answers with explicit safety boundaries.

What was built

A Next.js application with hybrid retrieval, grounding gates, language-specific prompting, three-check citation validation, pre-retrieval fatwa blockers, post-LLM refusal inspection, and a baked corpus fallback.

Retrieval

Hybrid BM25 plus semantic cosine retrieval over a 174-entry corpus. Pass 1 uses the original query; candidates are merged and filtered by coverage, BM25, and semantic thresholds.

Safety

34+ deterministic fatwa blockers and 19 prompt-injection patterns run before retrieval or generation. 26 post-LLM refusal patterns catch lazy fallbacks and prompt leakage; citations are stripped when refused.

Fallback

A 174-entry baked corpus snapshot (120 Shamail, 34 timeline, 20 courses) supports core answers when the live API is unavailable. Precomputed embeddings support semantic search when configured.

Technical implementation details

Citation validation

Three-check validation: corpus entry exists, has body text, and matches answer language. Citations come from retrieval, not model output. Coverage threshold ≥ 0.5, BM25 ≥ 8, semantic score ≥ 0.62.

Frontend gating

Source chips and share controls are shown only for responses with status `answered` and citations. Non-answer states cannot display citations.

Limitations

Semantic search depends on Gemini API availability; LLM synthesis requires valid API credentials.

02

HVAC Revenue Recovery System

Case study In Progress — Active Development

A safety-gated recovery pipeline for HVAC revenue leaks: signed webhooks identify unbooked estimates and dormant leads, workers classify and draft outreach, and human approval controls customer-facing execution.

Problem

HVAC contractors lose track of sent-but-unbooked estimates and cold leads. Manual follow-up is inconsistent, and automated outreach risks consent, compliance, and customer-trust failures.

What was built

A multi-tenant Next.js application with four workers, RLS-isolated PostgreSQL data, HMAC webhook verification, replay protection, idempotency, risk classification, approval workflows, rate limiting, circuit breakers, and audit logging.

Workflow

CRM/Webhook → Validation → Intelligence → Recovery → Safety → Human Approval → Execution → Audit.

Safety

Deterministic consent, opt-out, client policy, and kill-switch checks return ALLOW, BLOCK, or ESCALATE. Yellow-risk customer-facing actions require approval before execution.

Integrations

ServiceTitan and Twilio adapters, Zod validation, Supabase Auth, PostgreSQL with 22 migrations, and an operations dashboard for command, pipeline, safety, opportunities, tenants, integrations, and audit views.

Limitations

Technical case study under active development. No customer deployment, recovered revenue, ROI, or measured business outcomes are claimed.

Technical implementation details

Four workers

Intelligence scores opportunities and recommends strategy; Recovery drafts messages and classifies replies; Safety & Policy enforces consent, opt-out, policy, and kill switch; Operations records metrics, anomalies, and cost.

Webhook security

HMAC signature verification, replay protection, five-minute timestamp window, 1 MB payload cap, and idempotency keys. LLM output is schema-validated with Zod and never trusted blindly.

Risk and execution

GREEN / YELLOW / RED classification with human approval for yellow-risk actions. Execution uses rate limiting, circuit breakers, and an outbound queue to Twilio or a mock adapter.

Evidence

README-reported: 640 tests across 52 files and 22 database migrations. These are reported evidence, not independently verified results.
